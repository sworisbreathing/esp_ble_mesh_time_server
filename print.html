ESP BLE Mesh Time Server Documentation

ESP-BLE-MESH Time Server Component

ESP-BLE-MESH Time Server provides a BLE Mesh time server implementation which integrates ESP-BLE-MESH with the System Time API.

Features

  • Convenience macros for defining time state / time setup server / time server
  • Sanity checks to ensure time state is properly bound to time setup server / time server
  • BLE Mesh Time is integrated into system time:
    • Time Set message handlers update system time via settimeofday()
    • Time Status messages populate TAI time using gettimeofday()
    • Time Zone Set messages update system time zone via TZ/tzset()
  • Optional handling of TAI UTC Delta Set messages (opt-in)
  • Support for scheduled Time Zone / TAI UTC Delta updates
  • Hook for notifying when the system time has been updated by an out-of-band source

Motivations

The default (ESP_BLE_MESH_SERVER_AUTO_RSP) time server behaviour in ESP-BLE-MESH simply treats time as any other fixed data. It is only updated in response to a Time Set message, meaning subsequent Time Status messages will always return the same time value until the next Time Set message is received.

This isn’t how time works.

Furthermore, the default behaviour in ESP-BLE-MESH does not properly consider TAI of Zone Change or TAI of Delta Change when managing its internal state or sending a Time Status message.

When time is updated by an out-of-band source such as SNTP or GPS, ESP-BLE-MESH doesn’t provide a simple means of notifying that time has been updated. Instead, you’re required to roll your own code to:

  • convert from whatever time system your OOB time source uses to TAI time
  • keep track of current and future timezone changes to ensure your TAI time is converted correctly
  • keep track of current and future leap seconds/leap hours to ensure your TAI time is converted correctly
  • call esp_time_scene_client_set_state() to update the time state when the OOB time source updates the time (thus having to leak BLE Mesh model/context data to external code)

This component was created as an attempt to solve the above problems in as simple a way as is practical.

Long-term it is desirable to get fixes into ESP-BLE-MESH itself rather than having to rely on a third-party component, but for now, this will have to do.

Update Time From OOB Source

Nodes configured with Mesh Time Authority or Mesh Time Relay role publish unsolicited time status messages when their clocks are updated by an out-of-band (OOB) time source, such as SNTP or GPS.

Use oob_time_updated() after updating the system time (e.g. via settimeofday() or in an SNTP event handler) to publish these unsolicited time status messages.

static void sntp_event_handler(void *arg, esp_event_base_t base, int32_t id, void *data)
{
    (void)arg; (void)base; (void)id;
    const esp_netif_sntp_time_sync_t *evt = (const esp_netif_sntp_time_sync_t *)data;
    if (evt) {
        uint8_t uncertainty = // ... determine uncertainty in 10ms increments (1=10ms, 2=20ms, etc)
        oob_time_updated(uncertainty);
    }
}

Leap Seconds / Leap Hours

The General Conference on Weights and Measures voted in October 2026 to replace leap seconds with leap hours. Although this doesn’t officially take effect until May 2027, no further leap seconds are expected to be added to UTC in the interim.

Since a full leap hour is not expected to be added to UTC for several centuries, proper support for TAI-UTC Delta functionality is provided on an opt-in basis. The setting CONFIG_ESP_BLE_MESH_TIME_UTC_DELTA_ENABLE can be found in the menuconfig at Component Config -> ESP BLE Mesh Time Server -> Handle TAI-UTC Delta Set Messages.

When CONFIG_ESP_BLE_MESH_TIME_UTC_DELTA_ENABLE is off (which is the default), the TAI-UTC delta remains at a constant 37s. The time setup server will ignore the payload of any TAI-UTC Delta Set message and instead reply with the current fixed values.

Proper handling of TAI-UTC Delta Set messages can be enabled by configuring CONFIG_ESP_BLE_MESH_TIME_UTC_DELTA_ENABLE, at the expense of:

  • an additional esp_timer for handling scheduled TAI-UTC Delta updates
  • additional processing for Time Set messages / oob_time_updated()
  • additional processing when initialising/deinitialising the time server

Thread Safety

This library should be as thread-safe as the underlying ESP-BLE-MESH component, with the following exceptions:

OOB Time Updates

The current implementation of oob_time_updated() is normally called from a different FreeRTOS task (such as the default event loop) than the task which runs ESP-BLE-MESH code/callbacks (one of potentially several bluetooth profile tasks).

The following properties are modified by oob_time_updated() and thus could potentially fall prey to race conditions between the task which invokes oob_time_updated() and the tasks upon which ESP-BLE-MESH runs:

Properties which are written by oob_time_updated():

  • time state -> uncertainty
  • time state -> time authority (not to be confused with the time role named Time Authority)
  • time server -> publish TTL (temporarily set to 0 before being restored to its previous value)

Properties which are read by oob_time_updated():

  • time state -> uncertainty
  • time state -> time authority (not to be confused with the time role named Time Authority)
  • time state -> time role
  • time server -> publish address
  • time server -> publish TTL (temporarily set to 0 before being restored to its previous value)
  • time state -> current TAI-UTC Delta
  • time state -> current timezone offset

To mitigate the risk, it is recommended to:

  • refrain from sending Time Set messages to nodes with OOB time sources
  • configure nodes with OOB time sources with the Mesh Time Authority role instead of Mesh Time Relay or Mesh Time Client
  • read the publish TTL on nodes configured as Mesh Time Authority / Mesh Time Relay after changing it, to confirm it has been properly set

Scheduled Timezone / TAI Delta Changes

Scheduled updates to time zone offset or TAI-UTC delta (when processing a Set message with a TAI of change in the future) are implemented using esp_timer, which runs from a different FreeRTOS task than the bluetooth stack.

Properties which are read during scheduled timezone updates:

  • time state -> current TAI-UTC delta
  • when persistence is enabled:
    • time state -> current TZ offset

Properties which are written during scheduled timezone updates:

  • time state -> new TZ offset
  • time state -> TAI of timezone change
  • time state -> current TZ offset
  • when persistence is enabled:
    • persistent state -> new TZ offset
    • persistent state -> current TZ offset
    • persistent state -> TAI of timezone change

Properties which are read during scheduled TAI-UTC Delta updates:

  • time state -> current TAI-UTC delta

Properties which are written during scheduled TAI-UTC Delta updates:

  • time state -> new TAI-UTC delta
  • time state -> TAI of TAI-UTC delta change
  • time state -> current TAI-UTC delta
  • when persistence is enabled:
    • persistent state -> new TAI-UTC delta
    • persistent state -> current TAI-UTC delta
    • persistent state -> TAI of TAI-UTC delta change

To mitigate the risk, it is recommended to:

  • avoid updating the device timezone for daylight savings
  • prefer immediate timezone / TAI-UTC delta changes when sending the relevant Set messages
  • include the time zone when converting time to a string (e.g. include %z when calling strftime())

Settings Persistence

Settings persistence is enabled automatically when configuring BLE Mesh settings persistence (CONFIG_BLE_MESH_SETTINGS in sdkconfig or Component config -> ESP BLE Mesh Support -> Store BLE Mesh configuration persistently via menuconfig). If you wish to disable time server settings persistence while keeping the out-of-the-box ESP-BLE-MESH settings persistence, you can set CONFIG_ESP_BLE_MESH_TIME_SETTINGS=n in sdkconfig, or via menuconfig at Component config -> ESP BLE Mesh Time Server -> Persist time server settings.

When time server persistence is enabled:

  • The esp_ble_mesh_time_server_config_t passed to ble_mesh_time_init() must contain a valid NVS handle.
  • The NVS handle must remain valid until ble_mesh_time_deinit() is called
  • The following settings will be persisted as a blob to NVS Flash under the ble_mesh_time key (19 bytes plus blob overheads):
    • time role state
    • time state uncertainty
    • time state authority bit
    • current timezone offset
    • future timezone offset (including TAI of change)
    • current TAI-UTC delta
    • future TAI-UTC delta (including TAI of change)
  • ble_mesh_time_init() will:
    • restore the above persisted state (note: TAI-UTC delta is only restored when TAI-UTC delta functionality is enabled)
    • update the system timezone
    • execute any scheduled timezone / TAI-UTC delta updates for which the scheduled time has already passed (i.e. a schedule that was missed due to deep sleep)
    • restart any timers for future timezone / TAI-UTC delta updates for which the scheduled time is still in the future

FAQs

Time Zone

My code already manages the system timezone

The current implementation expects timezone to be managed through BLE Mesh. Hopefully this will be addressed soon.

Time Uncertainty

How should OOB time sources calculate uncertainty?

If your OOB source/library provides any documentation with regard to clock drift/skew, start with that, and measure or estimate processing time to come up with a reasonable value for uncertainty.

If you aren’t sure, provide a conservative estimate.

The argument to oob_time_updated() has 10ms resolution, so a value of 1 is an uncertainty of 10ms, 2 means 20ms. Uncertainties greater than 2.55s should be clamped to 255.

Why does uncertainty keep increasing?

The current implementation adds a fixed 30ms uncertainty for each hop through a time relay node. Future versions might make this configurable or do a smarter measurement/estimation.

Troubleshooting

My devices aren’t sending or receiving BLE Mesh time messages

First, rule out the simple stuff:

  1. Confirm the devices are powered on

  2. Confirm the devices are in range of each other and not falling prey to RF interference

  3. Confirm the devices are provisioned as nodes to the same BLE Mesh subnetwork

  4. Confirm the correct AppKeys are bound to the time server and time setup server

    Note: The BLE Mesh spec strongly recommends using a dedicated AppKey for the time setup server.

  5. Confirm your IDF version to rule out a long-standing bug.

    • 5.3 - requires 5.3.7 or higher
    • 5.4 - requires 5.4.5 or higher
    • 5.5 - requires 5.5.7 or higher
    • 6.0 - requires 6.0.4 or higher
    • 6.1 - requires 6.1.2 or higher

    Note: at the time of this writing, none of these IDF versions have been released yet.

If the node correctly handles Time Set / Time Get messages and the issue is limited to the handling of unsolicited Time Status messages (i.e. via oob_time_updated()), it’s likely related to the node’s time role:

  • ESP_BLE_MESH_TIME_NONE is the default. These nodes silently ignore unsolicited Time Status messages entirely.
  • ESP_BLE_MESH_TIME_AUTHORITY nodes can send unsolicited Time Status messages (i.e. via oob_time_updated()) but silently ignore any messages received from other nodes
  • ESP_BLE_MESH_TIME_RELAY nodes process incoming unsolicited Time Status messages and propagate them through the network. They can also send their own unsolicited Time Status messages.
  • ESP_BLE_MESH_TIME_CLIENT nodes process incoming unsolicited Time Status messages but don’t send/propagate them.

If the time role isn’t the issue, then the issue is likely related to publish/subscription settings or network topology:

  • Check the publish address of your Time Authority / Time Relay nodes
  • Check the subscription address of your Time Relay / Time Client nodes
  • Unsolicited Time Status messages are always sent with a TTL of 0. Nodes must be in direct communication with a Time Authority or Time Relay node in order to receive these messages.

The nRF Mesh app isn’t sending or receiving BLE Mesh time messages

See above. The most common reason this can happen is the byte alignment issue affecting older IDF versions.

The time displayed in the nRF Mesh app is slightly off from the time reported by my device

There are two bugs in nRF Mesh which could be affecting you.

  1. Older versions of nRF Mesh used the wrong TAI epoch. Updating nRF Mesh to the latest version should fix this issue.
  2. nRF Mesh doesn’t adjust for TAI-UTC delta when rendering human-readable time. I’m hoping to raise this soon, along with a PR to fix it.

My device’s system time isn’t updating

If none of the above troubleshooting steps helps, check the logs for a message such as

E (1234) ble_mesh_time: failed to set system time: ...

and note the error name at the end.

  • EPERM means your app doesn’t have permission to change the system time. On Linux targets, CAP_SYS_TIME is required.
  • If you see a different error name, please open an issue and provide as much detail as you can.

My device’s time zone isn’t updating

If none of the above troubleshooting steps helps, it’s possible you’re hitting one of the following issues:

  1. Insufficient memory to set the TZ environment variable. Check the logs for an error message saying failed to set TZ.

  2. You’ve encountered a race condition

  3. Something went wrong with tzset(). Unfortunately, tzset() doesn’t report errors. Check the logs for an info message saying time zone updated and note the values reported. If the numeric portions don’t match (ignoring +, -, <, >, and :), then this is likely to be the culprit.

    Successful tzset():

    I (1234) ble_mesh_time: time zone updated to <+1100>-11:00 (+1100)

    tzset() failure:

    I (1234) ble_mesh_time: time zone updated to <+1100>-11:00 (-0600)
